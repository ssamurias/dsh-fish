# 第三方插件约定（v1）

> 这份文档写给「想给大肥鱼加一件东西」的人。
> 它管的是：一个第三方插件要满足什么，才能被市场正常收录、装上不会坏事、我们愿意在 README 里提一句。
> 它不管：你的代码怎么写、你的功能值不值得做、你的插件能不能长期维护——那些由作者自己负责。

大肥鱼 v1.0.0 已经发布，下面的字段和契约都已经在真机上跑过。

---

## 0. 先说清楚位置

插件是 **DSH 插件**，不是大肥鱼主包的一部分。也就是说：

- 放在你自己的仓库里，单独发 npm 包；
- 用 `dsh plugin add` 装进 profile，装之前要给这个工具**放行**；
- 主包升级（`npm i @ssamurias/dsh-fish@latest`）不会覆盖你的代码，你也不用跟着主包改 `lib/`。

反过来，**不要**把插件目录塞进 `@ssamurias/dsh-fish` 仓库：主包的 `files` 白名单不带它，升级是整包替换，`git pull` 也可能把它冲掉，而且它会算进主包的测试绿线。

---

## 1. 怎么被找到：靠 keywords，不靠包名

插件市场（`dsh-market-ui` 等）的数据源是 npm registry 的搜索接口，检索键是 **`keywords:dsh-plugin`**，结果缓存 6 小时。

所以：

```json
{
  "keywords": ["dsh-plugin", "dsh-fish"]
}
```

- **`dsh-plugin` 必须有**。没有它，包名起得再像，市场也搜不到；只有别人按完整包名精确查才找得到。
- **`dsh-fish` 建议有**。这是我们筛「给大肥鱼用的插件」的那一列，也是你和其他 DSH 插件区分开的地方。
- 可选再加 `dsh-market`、`cordis-plugin` 这类宽词，不影响。

**包名**只是给人看的，不是索引键。建议：

| 用途 | 包名 | 例 |
| --- | --- | --- |
| 只对养鱼的人有意义 | `dsh-fish-<用途>` | `dsh-fish-mirror` |
| 通用 DSH 插件 | `dsh-<用途>` | `dsh-clipboard` |

不强制前缀。**前缀和关键词都不代表官方认证**——官方只有 `ssamurias/dsh-fish` 这一个仓库。

仓库另外打两个 GitHub topic：`dsh-plugin`、`dsh-fish`（topic 是 GitHub 上唯一能跨仓聚合的机制，tag 只是仓内版本号，搜不到别的仓库）。

## 2. `package.json` 里要写的东西

```json
{
  "name": "dsh-fish-mirror",
  "version": "0.1.0",
  "type": "module",
  "description": "让她能看见你放进来的那张照片（只说一句给她加了什么）。",
  "keywords": ["dsh-plugin", "dsh-fish"],
  "engines": { "dsh": ">=0.2.0" },
  "files": ["lib", "cordis.patch.yml", "README.md"]
}
```

逐条说：

- **`engines.dsh` 必填**。市场在安装前拿它和本地版本比对，不写就显示「兼容性未知」，用户要么不敢装，要么装完崩。
- **`description` 用中文一句话**，说清「给她加了什么」，不写「一个优雅的……」。市场列表直接展示这一行。
- **`README.zh-CN.md` 优先**：详情页按界面语言先读这个。
- **禁止 `preinstall` / `install` / `postinstall` 脚本**。市场的装前体检会标警告；更实际的问题是安装脚本常把旧版核心包拖进来，那个坑我们已经踩过一次。
- **`dependencies` 保持 `{}`**。需要的东西一律走宿主已经有的能力；真必须外部包，就在 README 里写清为什么，并接受市场收录时被单独标注。

## 3. 硬性条款（不满足就不提）

1. **不改她的数据。** `~/.dsh-fish/events.jsonl` 只读；不写 `config.json` 的人格相关键；不碰 `state.json`、`她的身份.md`。要留自己的状态，放插件自己的目录。
2. **不提供任何「改人格」的入口。** 没有性格设定、没有好感度、没有人设输入框。这是主包的立项前提，不是口味问题。
3. **不注册会改她人格或身份的工具。** 只说「不提供界面」不够——插件能直接注册工具，所以这条要落到工具这一层。工具只做「多一种能做的事」，不做「改她是谁」。
4. **工具必须能被她调到，也只能这样调到。** 装完把工具名写进 `config.json` 的 `tools.allow`（或设置页白名单）；不放行她调不到，也不知道自己有这只手。白名单只做加法。
5. **至少一条 `node:test`**，`npm test` 能跑通。不要求覆盖率，要求「你自己跑过」。
6. **工具名写具体。** `her_mirror`、`her_closet` 这种可以；`her_search`、`her_read` 这种抢通用词的不行。重名时宿主按注册顺序只留一个，所以重名要在 README 里标出来。

## 4. 可选：接素材契约

如果你这个工具是「读到一样东西」，可以按 [`素材契约（v1）`](./素材契约.md) 返回，她就有了出处和可引用的原话。**不接也完全能用**，只是读完就散、翻不到。

最小形状：

```json
{
  "dshFishMaterial": 1,
  "source": "mirror",
  "key": "avatar-2026-11-12",
  "kind": "fact",
  "facts": [{ "label": "文件", "value": "avatar.png", "url": "file:///…" }]
}
```

整段必须是一个 JSON 对象，别在外面包「以下是结果：」——认不出来就按普通文本处理。

## 5. 安全与边界

- 只读自己的数据目录（`~/.dsh-fish` 和插件自己的目录）；
- 不外发她说过的话、不发日记、不发事件流；
- 不 `eval` 外部文本，不把网页内容当代码跑；
- 要接 IM 走 HTTP 桥（`POST /dsh-fish/say`），不要在插件里做登录、存 cookie；
- 不自己起长期进程；需要定时就用宿主已有的调度。

第三方插件跑在宿主进程里，权限和宿主一样。上面这些不是「建议」，是我们按「装了一个陌生人写的代码」来对待的底线。

## 6. 给使用者的装前自查

装任何第三方插件之前，看四件事：

1. 它注册了哪些工具名？名字和功能对得上吗？
2. 有没有 `preinstall` / `install` / `postinstall` 脚本？
3. `engines.dsh` 写了吗？和你的版本合得上吗？
4. 它要不要读 `~/.dsh-fish`？只在 README 承诺「只读」而没有明说读哪些，就当没说。

市场里的「体检」只查脚本、体积、`engines`、是否 deprecated，**不查它会不会动她的人格**。第四条只能自己看。

## 7. 我们怎么提别人的插件

我们不做索引——发现已经由市场做了，再维护一份会过期。

我们只维护一份**短名单**：装过、跑过、读过代码的那几个，写清补了什么、核对到哪一天、有没有坑。名单里没有的，不代表它不好，只代表我们没看过。

要进名单：开一个 Issue，给仓库地址和一句话说明。我们会装一遍、跑一遍它的测试、读一遍它注册的工具，然后决定放不放进去——**收录不等于背书**，作者更新后我们也不承诺跟进。

## 8. 常见翻车

| 症状 | 原因 |
| --- | --- |
| 市场里搜不到 | 没写 `keywords: ["dsh-plugin"]`，或刚发布还没进索引（见下） |
| 装完界面没反应 | `cordis.patch.yml` 的 `id` 与包名对不上，或客户端模块没被 `inject` 拿到 |
| 别人装上一片白/报错 | `cordis.patch.yml` 里 `root` 写死了你自己机器的路径 |
| 升级主包后插件坏了 | 复制了主包 `lib/` 的代码并跟着改；应该只依赖公开接口 |
| 工具调用报错 | `execute` 返回的不是字符串，或抛异常没兜住 |
| 装完她行为变了 | 插件注册了会写她数据的工具——违反第 3 节 |

---

## 9. 发布之后多久能被搜到

npm 搜索索引有延迟，市场缓存 6 小时。所以：

- 刚发布时，让别人**按完整包名搜**（市场对新包有精确包名兜底，能立刻查到）；
- 或者等半天再搜关键词；
- 别因为「搜不到」就改包名——多半只是还没进索引。

---

## 10. 变更

这份约定随主包版本走。字段、契约、必需项有变化时，在本文件顶部加一行日期，并在 `CHANGELOG.md` 里记一条。破坏性变更会给一个版本的过渡期。
